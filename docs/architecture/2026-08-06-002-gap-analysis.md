# Gap Analysis — SupportForge AI

Status: as of 2026-08-06, based on direct code review (backend, frontend, ingestion, deployment) — not on
prior documentation. Companion doc: [`2026-08-06-001-hld-system-design.md`](./2026-08-06-001-hld-system-design.md).
See that doc's §4 for specific corrections made to `docs/agentic-pipeline.md` and
`docs/architecture/2026-08-03-001-hld-kb-code-retrieval.md`, which were found stale during this review.

Severity key: **Critical** (production blocker / data breach / silent data corruption) · **High** (real
functional or security gap, PRD commitment unmet) · **Medium** (quality/robustness risk, not blocking) ·
**Low** (polish, minor maintainability).

## 1. Security & multi-tenancy

| Gap | Severity | Evidence |
|---|---|---|
| No server-side check that the authenticated user belongs to the `ProjectId` they query | **Critical** | `ProjectId` is client-supplied on `ChatQueryRequest` (`ChatController.cs:134`); no ownership/membership check exists anywhere. Any authenticated user can read/query any other project's KB and code data. |
| No role-based access control | **High** | JWT claims carry only `sub`/`unique_name` (`JwtTokenFactory.cs:37-41`); no role claim, no `[Authorize(Roles=...)]` in any controller. PRD's Support-vs-Admin distinction doesn't exist. |
| Auth is a custom JWT, not Entra ID | **High** (PRD deviation) | `Program.cs:76-90` wires `AddJwtBearer` against a locally-issued HMAC JWT. No OIDC/Entra package referenced anywhere in `backend` or `frontend` (`SupportForge.Api.csproj`, `frontend/package.json` both confirmed). No MFA/conditional access. |
| Self-registration endpoint has no gate | **High** | `POST /api/auth/register` (`AuthController.cs:37-50`) is open to any anonymous caller indefinitely — no invite/admin-approval flow. |
| JWT signing key silently falls back to a random per-process key if unset | **Medium** | `JwtTokenFactory.cs:14-28` — documented via comment but a real production foot-gun: tokens invalidate on restart and across multiple instances. |
| No global exception-handling middleware / inconsistent error shape | **High** | No `UseExceptionHandler`/`IExceptionHandler`/`ProblemDetails` anywhere in the API. Unhandled exceptions fall through to ASP.NET Core defaults inconsistently per controller. |
| No input length/size caps outside chat endpoint | **Medium** | `ChatController.cs:99-125` validates query length/screenshot size; `ProjectsController`, `IngestionController`, `FeedbackController` have no equivalent caps. |

## 2. AI trust & evaluation

| Gap | Severity | Evidence |
|---|---|---|
| No offline eval set / golden dataset for the LLM-judge verifiers | **High** | `KbResearcherVerifier`, `CodeAnalyzerVerifier`, `VisionAnalyzerVerifier` are well-prompted but their real-world precision/recall is entirely unmeasured — confirmed via `backend/SupportForge.Api.Tests/Agents`, which only mocks `ILlmClient` and asserts control flow, never real output quality. |
| No groundedness check beyond literal leak detection | **High** | `DrafterAgent`'s `LooksLikeLeak` guard (`DrafterAgent.cs:152-169`) only catches verbatim code/doc quoting. A paraphrased hallucinated fact passes through completely undetected — nothing verifies drafted claims against `KbSnippets`/`VisionFindings`. |
| Feedback is captured but never used | **High** | `FeedbackController.cs:19-24` persists `FeedbackEntry` via `IFeedbackRepository`; repo-wide search confirms nothing else reads it — no analytics, no prompt-improvement loop, no fine-tuning signal. Dead-ended data. |
| Prompt-injection defense is instructional only | **Medium-High** | Untrusted KB/code snippets are interpolated directly into prompts (`DrafterAgent.cs:109-117`) with no structural delimiters (XML tags, "treat as data" framing) — only a soft system-prompt instruction. |
| Verifier retry cap hardcoded, not configurable | **Low** | `Attempts < 2` duplicated identically across three verifier files. |
| Graceful degradation on total verification failure — **this is done well** | — | `DrafterAgent.HasNoUsableContext` short-circuits to a confidence-0.0 fallback message rather than a broken response (`DrafterAgent.cs:28-35`). |

## 3. Retrieval & data pipeline

| Gap | Severity | Evidence |
|---|---|---|
| Pinecone (PRD's stated production vector store) is unimplemented | **Critical** (PRD-blocking) | `VectorStoreServiceCollectionExtensions.cs:20` throws `NotSupportedException` for any provider other than `"Chroma"`. Only one concrete `IVectorStoreService` exists. |
| Cross-repo Neo4j node collision within a project | **High** | `GraphImportJob.cs:56` merges on `{id, projectId}` only, where `id` is the repo-relative file path. Two repos in the same project with identically-pathed files (e.g. both have `src/index.ts`) silently overwrite each other's graph node — real data corruption specific to the PRD's stated multi-repo use case. |
| No freshness webhooks / scheduled re-ingestion / staleness alerts | **High** (PRD deviation) | No webhook endpoint exists anywhere (repo-wide search confirmed). No `IHostedService`/timer re-triggers ingestion on a schedule. `FreshnessController` is a passive on-demand GET only — PRD explicitly requires all three. |
| Ingestion queue is in-memory only, no dead-letter handling | **High** | `IngestionQueue.cs:9` — `Channel.CreateUnbounded<IIngestionJob>()`, purely in-process. Crash/restart silently drops queued and in-flight jobs; permanently-failing jobs are only logged, not re-queued or surfaced to an operator. |
| Orphaned chunks never deleted on source shrink | **Medium-High** | `KbVectorIndexer` never calls `DeleteAsync`; if a document shrinks, trailing stale chunk IDs persist in Chroma forever, silently polluting retrieval. |
| Chunking has zero overlap, minimal metadata | **Medium** | `DocumentChunker.cs:9-31` — fixed 1000-char greedy word-wrap, no sentence/paragraph awareness, no overlap between chunks, metadata limited to `source`+`chunk index`. |
| Full re-chunk/re-embed on every ingestion run (no diffing) | **Medium** | `DocumentIngestionJob.cs:31-38` reprocesses the entire source set each run; idempotent via deterministic chunk IDs, but wasteful and doesn't scale with source-set growth. |

## 4. Reliability & cost

| Gap | Severity | Evidence |
|---|---|---|
| No runtime LLM provider fallback | **Medium** | Exactly one `ILlmChatClient` registered per process (`LlmServiceCollectionExtensions.cs:41,79,85`); a provider outage degrades every agent with no automatic failover. |
| Uneven resilience across providers | **Medium** | OpenAI and Anthropic have Polly retry+circuit-breaker; `BedrockLlmClient` relies solely on the AWS SDK's built-in retry, a materially different and less observable policy. |
| No open-source / self-hosted LLM provider option | **Medium** | All 5 registered providers (OpenAI, NVIDIA NIM, Azure OpenAI, Anthropic, Bedrock — `LlmServiceCollectionExtensions.cs:22`) are paid hosted APIs. No Ollama (or equivalent local-model) option exists, limiting cost-control and data-residency choices the PRD's "cost-efficient operation" objective would benefit from. |
| No model tiering / cost budgets | **High** (PRD deviation) | Every agent — cheap intent classifier and expensive final drafter alike — shares one configured model. Token usage is recorded (`ITokenUsageRepository`) but never gated or alerted on. |
| No metrics export / Application Insights | **Medium-High** (PRD deviation) | OpenTelemetry tracing is real and well-wired; no `WithMetrics()` pipeline, no Azure Monitor/App Insights exporter package anywhere. |
| No Neo4j health check | **Medium** | `/health` covers Chroma (live query) and LLM (DI resolution only); Neo4j — a hard dependency for all code Q&A — has no check, so an outage is invisible to `/health`. |

## 5. Operability & delivery

| Gap | Severity | Evidence |
|---|---|---|
| No deployment automation | **High** | `docs/deployment/*-runbook.md` are prose-only manual IIS click-through instructions; no IaC, no deploy script. "Rollback" is a manual folder swap. |
| Two unreconciled deployment models | **Medium** | A working `Dockerfile`/`docker-compose.yml` exists for local/CI use, but the production runbook doesn't use containers at all — nothing bridges the two. |
| CI has no frontend step, no deploy job | **Medium** | `.github/workflows/ci.yml` builds/tests the backend and builds a Docker image; frontend build/lint/vitest never runs in CI; the Docker build step doesn't push or deploy anywhere. |
| Single-instance architecture, no horizontal scaling path | **High** (long-term) | In-process `Channel` queue and in-memory state (`ConcurrentDictionary`), `AddSingleton` — a second instance would run a disconnected queue/state. Acceptable at PRD's stated "10+ projects" scale, not beyond. |
| No project onboarding documentation | **High** (PRD objective unmet) | No root `README.md` at all; `frontend/README.md` is unmodified Vite boilerplate. PRD lists "easy onboarding of new projects" as an objective with nothing in `docs/` explaining how. |
| `docs/agentic-pipeline.md` and the KB/code-retrieval HLD are stale | **Medium** | See companion HLD doc §4 — both describe a pipeline/retrieval architecture the code has since replaced. Actively misleading to a new reader until corrected. |

| Gap | Severity | Evidence |
|---|---|---|
| No citations/sources shown to the user | **High** | `MessageBubble.tsx`/`MessageThread.tsx` display no source attribution despite this being a retrieval-grounded product — PRD explicitly calls for "cited sources (KB + Code with file/repo links)". |

| Committed `.env.production` with a placeholder host | **Low** | `frontend/.env.production` is tracked in git with a hand-edit-per-deploy placeholder — not a secret leak, but an inconsistent pattern vs. the correctly-ignored `.env`. |

## 7. What's genuinely well built (don't regress these)

- The verifier/retry/graceful-degradation pattern (`KbResearcherVerifier` → retry-once → `FailedFinal` →
  `DrafterAgent.HasNoUsableContext` fallback) is a legitimate lightweight quality gate, correctly implemented.
- Purpose-aware embeddings (`EmbeddingPurpose.Query` vs `.Passage`) correctly avoid the train/query mismatch
  that silently degrades many RAG systems.
- Per-request OpenTelemetry tracing with structured per-agent decision logging is real, not cosmetic.
- Backend test coverage is broad and largely uses genuine `WebApplicationFactory` integration tests, not
  shallow mocks-only unit tests.
- `.gitignore` correctly excludes local data directories (`.chroma-data/`, `.neo4j-data/`) and the real
  `appsettings.Development.json` secret — confirmed not tracked via `git ls-files`.
- Removing the external `graphify` CLI subprocess in favor of an in-process extractor eliminates an entire
  class of external-tool availability/versioning risk (traded for lower extraction fidelity — see §3).
