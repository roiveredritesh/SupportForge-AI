Why we're building this

Support engineers answer the same class of question across many projects, from scattered sources.

Every new project means re-learning its docs, its repos, and its recurring errors from scratch. SupportForge AI centralizes that retrieval and reasoning into one reusable pipeline, so onboarding a project is a config change, not a new build.

  • 40–60%reduction targeted in average ticket resolution time
  • 10+projects supported concurrently on one shared pipeline
  • 1config-driven onboarding flow — no per-project code fork
  • <12starget end-to-end response time for most queries
Support EngineerPrimary daily user, asks questions, gets cited answers
Support Lead / AdminConfigures projects, monitors freshness & usage
Engineering ContributorFeeds KB and code sources into the index

What "plug-and-play" means here

Each project registers its GitHub repos, KB sources (Confluence, docs, websites), and access rules through the Admin UI. The same six-agent pipeline then serves every project — retrieval is scoped by project, not rebuilt per project. Ingestion runs continuously in the background so answers stay current as repos and docs change.

04 / 05
What it's built on

A resilient platform, not a single-vendor prototype.

The MVP shipped on one LLM and one vector store; both are now abstracted so the platform can fail over or be re-priced without a rewrite.

Frontend React

  • React 18 + TypeScript + Vite, Tailwind / shadcn UI
  • Query page with streaming (SSE) status: Triage → Research → Drafting
  • Cited sources rendered inline with the answer
  • Admin views for project, KB source, and repo configuration

Backend .NET

  • .NET 8/9 + ASP.NET Core on IIS, deploy scripted for CI
  • Microsoft Agent Framework drives the verified workflow
  • Project-membership access control on every API route
  • Metrics pipeline with optional Application Insights / Azure Monitor export

Model Layer Multi-provider

  • Anthropic, OpenAI, and Bedrock clients behind one interface
  • Ollama supported for self-hosted / open-source models
  • Automatic fallback chain if a provider fails or rate-limits
  • Optional model tiering — cheaper models for Triage & verifiers

Data & Freshness Chroma / Pinecone

  • Chroma locally, Pinecone in production, behind IVectorStoreService
  • GitHub webhooks + scheduled resync keep the code index current
  • Confluence webhook for push-triggered KB re-sync
  • Dead-letter visibility for ingestion jobs that permanently fail
